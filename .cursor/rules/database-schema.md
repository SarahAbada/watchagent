# Database Schema & Engine Architecture Conventions

## Context
This project utilizes an embedded SQLite database. Because the application runs in a containerized environment exposed to potential weather-induced power disruptions, uncoordinated restarts, and external API payloads, the database must prioritize absolute data persistence, strict parameterization, and crash resilience.

## Storage Engine & Container Persistence Configuration
- **Database Choice:** Use SQLite via the standard library `sqlite3` module or an async equivalent (like `aiosqlite`). Do not spin up an external database container.
- **Persistence Architecture:** The database file must not be stored in the container's ephemeral root directory. It must reside in a dedicated data directory (e.g., `/app/data/weather.db`) configurable via a `DATABASE_PATH` environment variable. This allows the file system to persist across Docker container lifecycle restarts via volume mounts.
- **Resilience Pragmas:** Every database connection initialization must execute the following optimization pragmas to prevent data corruption during unexpected outages:
  ```sql
  PRAGMA journal_mode = WAL; -- Write-Ahead Logging for crash resilience
  PRAGMA synchronous = NORMAL; -- Balances disk safety and write speeds
  PRAGMA foreign_keys = ON; -- Enforce relational database integrity
  ```

## Security & Query Hardening (SQL Injection Neutralization)
- **Parameterized Queries Only:** Cursor is strictly forbidden from generating any database queries that use Python string formatting, f-strings, or string concatenation to insert variables into SQL commands. All queries must exclusively use parameterized placeholders (e.g., `?` syntax) to neutralize SQL injection or malicious inputs.
- **Runtime Schema Immobility:** No application code may execute schema-modifying commands (`DROP TABLE`, `ALTER TABLE`, `CREATE TABLE`) during standard runtimes. Table creation scripts must only execute once during initial application startup using `IF NOT EXISTS` syntax.

## Table Schemas & Constraints
Cursor must enforce this precise layout when generating database migration or initialization scripts:

1. **`weather_readings` Table** (Stores deduplicated raw conditions)
   - `id`: INTEGER PRIMARY KEY AUTOINCREMENT
   - `city`: TEXT NOT NULL
   - `timestamp`: TEXT NOT NULL (Enforce strict ISO 8601 format strings)
   - `temperature_2m`: REAL NOT NULL
   - `apparent_temperature`: REAL NOT NULL
   - `precipitation`: REAL NOT NULL
   - `wind_speed_10m`: REAL NOT NULL
   - `weather_code`: INTEGER NOT NULL
   - **Constraint:** `UNIQUE(city, timestamp)`

2. **`notable_events` Table** (Stores historical streams generated by the AI agent)
   - `id`: INTEGER PRIMARY KEY AUTOINCREMENT
   - `city`: TEXT NOT NULL
   - `timestamp`: TEXT NOT NULL (ISO 8601 string when the event occurred)
   - `event_type`: TEXT NOT NULL (e.g., 'EXTREME_TEMP', 'SUDDEN_PRESSURE_DROP')
   - `rationale`: TEXT NOT NULL (Explaining why the system considered it notable)
   - `payload_snapshot`: TEXT NOT NULL (JSON string snapshot of the reading that triggered it)

3. **`polling_metrics` Table** (Aggregated long-term uptime statistics)
   - `hour_bucket`: TEXT NOT NULL (ISO 8601 string truncated to the hour, e.g., '2026-05-28T15:00')
   - `total_polls`: INTEGER DEFAULT 0
   - `failed_polls`: INTEGER DEFAULT 0
   - **Constraint:** `PRIMARY KEY (hour_bucket)`

## Data Querying Rules
- **JSON Handling:** The `payload_snapshot` in the events table must be serialized/deserialized safely using Python's standard `json` library.
